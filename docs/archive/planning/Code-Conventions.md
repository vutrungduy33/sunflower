# 新增代码统一规范

> 更新时间：2026-03-13
> 适用范围：`sunflower-backend`、`sunflower-admin-web`、`sunflower-miniapp` 以及相关脚本/文档

## 1. 目标

- 后续新增代码默认遵循本规范，保证同一子系统内的目录结构、命名方式、状态处理和测试要求保持一致。
- “统一风格”不等于强行把 Java、TypeScript、微信小程序写成同一种语法风格；统一的是分层方式、复用原则、命名语义和提交流程。
- 如与更近一层的专项文档冲突，优先级按以下顺序执行：
  1. `docs/API.md` / `docs/API-Schemas.md`
  2. `docs/Web-Admin-Plan.md`
  3. 本文档

## 2. 通用规则

### 2.1 目录与分层

- 优先沿用现有目录，不新开第二套并行结构；新增文件必须放入当前子系统已有分层中。
- 页面/控制器只负责输入输出、路由和生命周期编排，业务规则放到 service、feature、utils 或 persistence 层。
- 共用逻辑优先抽到现有公共目录，不在多个页面/模块内复制同一份请求拼装、状态转换或格式化逻辑。

### 2.2 命名与文案

- 代码标识符、文件名、接口字段名统一使用英文；页面标题、按钮文案、提示文案统一使用中文。
- 命名必须表达业务语义，避免 `data1`、`temp`、`handleOk2` 这类无语义名称。
- 新增状态值、枚举值、事件名、埋点名必须与现有领域词汇保持一致，不为同一概念再造别名。

### 2.3 配置、常量与注释

- 禁止在业务代码中硬编码环境地址、token、端口、时间窗口和状态文案；统一走配置、常量或服务层封装。
- 优先复用现有 DTO、响应包装、常量和工具函数；只有现有抽象无法覆盖时才新增。
- 注释只解释业务约束、边界条件和不直观的实现原因，不写重复代码字面的注释。

### 2.4 变更边界

- 默认保持 API 向后兼容；若必须改动契约，必须同步更新调用端、`docs/API.md`、`docs/API-Schemas.md` 和自动化测试。
- 若改动命中 `db/migration`、`persistence` 或核心事实源，必须同步检查 `scripts/sql/mvp_demo_seed.sql` 是否需要更新。
- 不为单次需求引入过重的新框架、新状态管理库或第二套 UI 组件体系。

### 2.5 测试与交付

- 每次新增业务能力至少覆盖 1 条自动化校验，并补齐成功路径和失败/空态中的至少一种。
- 面向交付的改动必须提供人工复核步骤，能让 QA 按步骤复现。
- 合并前至少运行与改动匹配的检查命令，例如 `mvn test`、`npm run lint`、`npm run test` 或 `npm run build`。

## 3. Spring Boot 后端规范

### 3.1 模块组织

- 继续使用 `modules/<domain>` 作为主目录；管理端能力放在 `modules/<domain>/admin`。
- 请求/响应对象放在 `dto`，持久化对象与 repository 放在 `persistence`，不要把 controller DTO 和 persistence entity 混在一起。
- 新增管理接口时，优先复用现有 `ApiResponse` 包装和统一错误语义。

### 3.2 职责边界

- Controller 保持薄层：只做参数接收、校验、鉴权入口和响应包装，不内嵌复杂业务编排。
- Service 承担状态流转、事务边界和业务规则；Repository 只负责数据访问，不承载业务判断。
- 新增写操作优先考虑事务一致性、库存/状态并发安全和幂等语义，不在 Controller 中拼事务逻辑。

### 3.3 数据与校验

- 请求参数优先使用 Bean Validation，避免把空值、格式和范围校验散落在业务代码中。
- 时间、金额、库存、状态等核心字段使用明确类型和命名，避免字符串魔法值横飞。
- 涉及列表查询时，先复用现有查询条件和排序口径，避免同一后台页面拿到两套不一致数据定义。

## 4. Web 管理后台规范

### 4.1 目录组织

- `src/app` 放路由、导航、布局和应用级装配。
- `src/features` 放业务域的 API、查询、表单转换和复用逻辑。
- `src/pages` 只放路由页面容器，不把大量请求封装和公用转换函数堆进页面文件。
- `src/services` 放 HTTP 客户端与跨域通用服务，`src/styles` 放共享样式和变量，`src/test` 放测试基建与页面测试。

### 4.2 组件与状态

- 优先使用 `TDesign React` 组件；只有明确存在功能缺口时才新增自定义组件，并保持为薄封装。
- 服务端状态统一通过 `TanStack Query` 管理；页面临时交互状态使用局部 React state，不额外引入 Redux 一类全局状态库。
- 新页面必须补齐加载态、空态、错误态和成功反馈，保持与现有后台页面一致的交互语义。

### 4.3 请求、路由与构建

- 所有接口请求统一通过 `src/services/http.ts` 或 feature service 封装发起，禁止在页面里直接写裸 `axios` 和完整后端地址。
- 新增业务页默认接入路由级懒加载，避免重页面再次回到首屏主包。
- 若某页面引入重型依赖导致构建体积异常，优先拆页面和依赖边界，再考虑手工 chunk 策略。

### 4.4 样式与测试

- 样式优先复用现有类名、变量和布局语义，不在页面内堆大量一次性内联样式。
- 文件命名延续现有 `kebab-case` 约定，例如 `room-management-page.tsx`、`admin-room-service.ts`。
- 页面和业务流程测试优先使用 `Vitest + Testing Library`，至少覆盖列表加载、表单校验、保存成功或失败中的关键路径。

## 5. 微信小程序规范

### 5.1 组件与目录

- 优先使用 `tdesign-miniprogram`；新增自定义组件前先确认 TDesign 现有组件和组合方式无法满足需求。
- 业务页面继续放在 `pages/mvp/*`，复用逻辑优先放到 `utils/mvp/*`、`behaviors/*` 或现有组件目录。
- 不把示例页、演示页的写法直接复制到正式业务页面。

### 5.2 页面逻辑

- 页面文件只保留生命周期、导航和 `setData` 驱动逻辑，请求调用、数据归一化和埋点封装下沉到 `utils`。
- 异常处理要落到用户可理解的中文提示，避免直接透出原始异常对象或接口字段。
- 页面跳转、登录复用、埋点事件名称优先沿用现有 MVP 主链路术语，避免同一行为出现多套埋点名称。

## 6. 文档同步要求

- 新增模块、页面、接口或约束后，要把入口同步到对应文档，避免“代码已落地、文档无索引”。
- 至少检查以下文档是否需要同步：
  - `README.md`
  - `docs/README.md`
  - `docs/MVP-Readiness.md`
  - `docs/MVP-Progress.md`
  - `docs/Project-State.md`
  - `docs/API.md` / `docs/API-Schemas.md`

## 7. 提交前自检清单

1. 本次改动是否仍然聚焦在一个清晰目标内。
2. 是否沿用了现有目录分层，而不是新开一套模式。
3. 是否复用了现有 UI、HTTP、DTO、状态和值域定义。
4. 是否补了自动化检查与人工复核步骤。
5. 是否同步更新了受影响的文档入口。
