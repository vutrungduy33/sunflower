- 本 Stage 目标：清理正式上线前的部署与域名阻塞项，统一 prod 配置归属，并将发布链路升级为“双 ECS + 构建并行 + 切流串行”的稳定方案。

- 关键实现点：
  - 将生产发布拓扑拆成双 ECS：ECS-2 运行 `mysql + backend`，ECS-1 运行 `admin-web + host nginx`，ECS-1 通过内网 upstream 访问 ECS-2。
  - 新增 `docker-compose.backend.yml` 与 `docker-compose.web.yml`，保留原 `docker-compose.yml` 作为本地单机联调入口，不把本地开发链路一起打散。
  - 发布脚本增加 `DEPLOY_NODE_ROLE=backend|web` 角色感知；backend 节点只处理 backend/mysql，web 节点只处理 admin-web/nginx。
  - `reload_host_nginx.sh` 改为等待远端 backend upstream 健康，再刷新 ECS-1 宿主机 Nginx；admin 域名同时代理本机 `/` 和远端 `/api/`，避免后台浏览器额外 CORS 改造。
  - `deploy-backend.yml` 重构为 4 段链路：`detect-targets -> build-backend/build-admin-web(并行, 导出 artifact) -> deploy-backend-host(self-hosted) -> deploy-web-host(self-hosted)`。
  - 两个 deploy job 分别固定到 `ecs-backend` 与 `ecs-web` runner label；backend artifact 只由 ECS-2 下载，admin-web artifact 只由 ECS-1 下载，ECS-1 不再中转 backend 构建产物。
  - 新增 `scripts/sync_deploy_bundle.sh` 与 `scripts/execute_runner_deploy.sh`，在目标机本地同步 bundle、生成 `.release.env` 并调用既有部署脚本，常规发布不再依赖 SSH/SCP。
  - `target=all` 与 `target=bootstrap` 现在固定执行 `ECS-2 backend -> ECS-1 admin-web -> ECS-1 nginx reload`，只改 backend 或只改 admin-web 时会自动跳过另一台主机。
  - `.env.prod` 模板拆成 backend/web 两份示例，避免把数据库、微信、短信等敏感配置混放到 web 节点。
  - 发布脚本优先复用 artifact 预加载到本地的镜像；只有本地镜像不存在时才回退到 `docker pull <image>`，保留 `workflow_dispatch + image_tag` 的 GHCR 回滚接口。
  - 文档、Runbook、验收清单已同步更新到双 ECS 口径。

## 风险与后续

- 当前已知风险：
  - 两台 self-hosted runner 需要运维保证持续在线，并确保 runner 用户具备 Docker 与 `$DEPLOY_PATH` 的写权限；否则发布链路会卡在 job 排队或本地 bundle 同步阶段。
  - 宿主机 HTTPS 证书仍需由运维先行签发并分别落到 ECS-1 的 `HOST_NGINX_ADMIN_TLS_CERT_PATH` / `HOST_NGINX_ADMIN_TLS_KEY_PATH` 与 `HOST_NGINX_API_TLS_CERT_PATH` / `HOST_NGINX_API_TLS_KEY_PATH`。
  - ECS-2 的 `8080` 必须通过安全组限制为仅允许 ECS-1 私网访问；否则会失去“备案入口统一在 ECS-1”的安全边界。
  - 当前仍使用自建 MySQL 容器；若后续流量增长，建议在 `S20` 之后评估 RDS/备份与监控增强。
- 下一 Stage 建议：
