# Agent 分阶段开发计划（V1）

> 更新时间：2026-03-13
> 目标：把当前已完成的 S0-S15 交付继续收口到可正式上线的 V1（小程序 + 后端 + Web 管理后台），并确保每个 Stage 可在一次与 Agent 的对话中完成“开发 + 测试 + 文档同步”。

## 1. 当前事实基线（2026-03-13）

- 小程序 MVP 前端主链路已完成：首页、房型详情、提交订单、模拟支付、订单中心、改期申请、退款申请均可联调运行。
- 后端已完成 MySQL + Flyway 持久化、房型/用户/订单事实源落库、订单分层状态机（`bookingStatus/paymentStatus/afterSaleRequest`）和管理端核心 API。
- Web 管理后台已完成工程骨架、登录守卫、房型管理、价格库存、订单与售后、经营概览等页面。
- CI/CD、联调验收清单、发布与回滚 Runbook 已具备，S14/S15 已完成。
- 当前距离“正式上线 V1”仍有明确缺口：
  - 小程序微信登录虽已接入 `wx.login -> code2Session` 方向，但默认仍保留 mock OpenID 开关；手机号绑定仍是业务接口，未切到微信官方手机号能力主流程。
  - 管理端登录仍基于静态 `app.admin.auth.token`，没有后台账号表、手机号绑定、密码登录、短信验证码重置能力。
  - 支付与退款仍是模拟状态流转，没有真实微信支付下单、回调、退款回调、支付流水和对账能力。
  - 正式环境入口、HTTPS、微信后台合法域名、微信支付回调域名、生产密钥与发布烟测仍需统一收口。

## 2. V1 最终开发目标（本轮确认）

V1 完成标准（上线就绪）：

1. 小程序用户身份链路为真实微信认证：采用微信开放文档当前主流方案 `wx.login -> auth.code2Session -> 后端签发业务 token`，手机号绑定采用 `getPhoneNumber` 组件 + 后端调用 `phonenumber.getPhoneNumber`，开发环境仅保留显式 mock 开关，不允许生产环境默认 mock。
2. 住宿订单资金链路闭环：创建、支付、取消、改期申请、退款申请、退款回调、入住、离店、失约全部基于真实状态机与支付流水，不再以“模拟支付”作为上线前提。
3. Web 管理后台具备真实账号体系：后台账号绑定手机号、设置密码、通过手机号 + 密码登录，并支持短信验证码重置密码；权限至少收口到 `admin/operator` 两个最小角色。
4. 具备可正式发布的生产能力：HTTPS 域名、微信小程序合法域名、微信支付回调域名、环境变量与密钥管理、联调烟测、回滚说明全部可执行。
5. 具备可重复验证能力：后端自动化测试 + 管理后台基础自动化测试 + 小程序人工验收清单 + 发布前 smoke test。

说明：

- P1/P2（商品、服务订单、社区深度运营等）不作为 V1 阻塞项，在 V1 收口后进入下一轮 Stage。
- V1 现在的核心收口主线只有四条：`真实认证`、`真实支付/退款`、`后台账号安全`、`生产发布阻塞项`。

## 3. Stage 执行规则（强约束）

每个 Stage 必须满足：

1. 单次对话内完成：需求确认 -> 编码 -> 测试 -> 结果回传。
2. 只做一个主题，不跨多个大模块。
3. 保持 API 契约兼容或同步更新调用端。
4. 必须有“可执行测试”与“可人工复核步骤”。
5. Stage 完成后必须更新对应文档（至少 `docs/Backlog.md` 勾选状态）。
6. 若 Stage 涉及“数据迁移/持久化入库”变更（迁移脚本、`persistence` 层、核心事实源入库逻辑），必须同步更新 `scripts/sql/mvp_demo_seed.sql`，并确认 `scripts/start_backend_with_mvp_seed.sh` 仍可自动导入演示数据。

## 4. 对话执行模板（每个 Stage 通用）

建议对 Agent 使用固定指令模板：

```text
请执行 Stage Sx（名称），要求：
1) 完成该 Stage 的代码改动
2) 运行并汇报测试结果
3) 更新文档中的 Stage 状态
4) 列出风险与下一 Stage 建议
```

Agent 回传结果至少包含：

1. 改动文件列表
2. 测试命令与结果
3. 手工验证步骤
4. 未解决风险

执行约束（建议强制）：

1. 开始前运行：`./scripts/stage_guard.sh pre Sx`
2. 完成后更新：`docs/stage-reports/Sx.md`
3. 结束前运行：`./scripts/stage_guard.sh post Sx`
4. 分支命名：`codex/s<stage>-<slug>`（例：`codex/s1-db-migration`）
5. 提交前缀：`[Sx] ...`（例：`[S1] add flyway migration`）
6. 执行 DoD 清单：`docs/Definition-of-Done.md`
7. PR 门禁必须通过：Stage Guard + 自动化测试
8. 涉及“数据迁移/持久化入库”时，`stage_guard post` 必须通过 seed 同步校验（`scripts/sql/mvp_demo_seed.sql`）

### S15 订单状态机重构（即时确认 + 售后子状态）

- 目标：将住宿订单从“单一 status”升级为“主订单状态 + 支付状态 + 售后申请状态”模型，并保持现有小程序/管理端兼容可用。
- 开发范围：
  - 为订单新增 `bookingStatus`、`paymentStatus` 事实字段，并保留 `status/statusLabel` 作为兼容展示字段。
  - 新增 `order_after_sale_requests` 持久化表，支持退款/改期申请的提交、审批、拒绝与历史保留。
  - 用户端 `/api/orders/{id}/reschedule`、`/api/orders/{id}/refund` 调整为“提交申请”语义。
  - 管理端新增入住、离店、失约，以及售后申请审批/拒绝接口；原有后台直接改期/退款接口保留兼容。
  - 同步小程序订单中心、管理后台订单页、API 文档与 Schema 文档。
- 本 Stage 边界（不做）：
  - 不接入真实微信支付/退款回调。
  - 不升级后台账号体系或 RBAC。
  - 不扩展餐饮/服务订单等新业务。
- 必做测试：
  - `cd sunflower-backend && mvn test`
  - `cd sunflower-admin-web && npm run test`
  - `cd sunflower-admin-web && npm run build`
  - 小程序订单页手工验证：提交改期/退款申请、查看申请状态。
- 完成标准：
  - 订单支持 `PENDING_PAYMENT / CONFIRMED / CHECKED_IN / CHECKED_OUT / CANCELLED / NO_SHOW` 主状态。
  - 售后申请支持 `REQUESTED / APPROVED / REJECTED / WITHDRAWN`。
  - 旧 `status/statusLabel` 字段继续可用，现有前端页面不会因状态机升级而失效。

### S16 小程序真实微信认证与手机号绑定

- 目标：把当前开发态可用的微信登录链路收口为正式上线可用的认证方案。
- 开发范围：
  - 小程序登录统一采用微信官方主流流程：`wx.login` 获取临时 `code`，后端调用 `auth.code2Session` 换取 `openid/session_key/unionid(若可用)`，再签发业务 token。
  - 默认关闭 `app.auth.wechat.mock-enabled`，仅开发/测试环境允许显式开启 mock；生产环境配置缺失时应启动失败而不是降级为 mock。
  - 小程序手机号绑定切换为官方 `getPhoneNumber` 组件主流程，后端消费动态 `code` 调用 `phonenumber.getPhoneNumber` 获取手机号；当前手输手机号仅保留为开发兜底或后台修复手段。
  - 完善登录态过期、重新登录、注销、首登建档和用户隐私同意流程。
  - 同步更新小程序交互、后端认证配置、API 文档和环境变量说明。
- 本 Stage 边界（不做）：
  - 不接入微信支付。
  - 不改造后台账号体系。
- 必做测试：
  - `cd sunflower-backend && mvn test`
  - 小程序手工验证：首次登录、登录态失效后重登、手机号授权成功/拒绝、mock 关闭时的配置校验。
- 完成标准：
  - 生产环境不再依赖固定 OpenID 或默认 mock 登录。
  - 小程序主登录链路和手机号绑定链路均采用微信官方能力。
  - 认证失败、凭证过期、手机号授权拒绝的端到端提示清晰可复现。

### S17 管理端真实账号登录（手机号 + 密码 + 短信重置）

- 目标：替换静态管理 token，建立后台最小可用账号体系。
- 开发范围：
  - 新增后台账号、账号凭证、密码重置验证码等持久化表与迁移脚本。
  - 登录方式升级为“手机号 + 密码”，密码必须加密存储（建议 `BCrypt` 或同等级安全方案）。
  - 管理端账号支持绑定手机号、初始化设置密码、修改密码、退出登录。
  - 新增短信验证码发码与校验流程，用于“忘记密码/重置密码”；需补齐有效期、次数限制、频率限制、验证码作废和审计字段。
  - Web 管理端登录页、重置密码页、登录态存储、接口拦截器、退出登录流程同步升级。
  - 最小权限模型收口为 `admin/operator`，并保留后续扩展 RBAC 的接口和数据结构空间。
- 本 Stage 边界（不做）：
  - 不做完整 RBAC 配置后台。
  - 不接入企业微信、LDAP 或第三方 SSO。
- 必做测试：
  - `cd sunflower-backend && mvn test`
  - `cd sunflower-admin-web && npm run test`
  - `cd sunflower-admin-web && npm run build`
  - 手工验证：手机号登录成功/失败、密码重置、验证码过期、连续失败限制。
- 完成标准：
  - 管理端主登录链路不再依赖 `app.admin.auth.token`。
  - 后台账号可通过手机号 + 密码登录，并可通过短信验证码完成密码重置。
  - 最小权限与登录审计可支撑正式运营使用。

### S18 真实微信支付/退款与资金流水

- 目标：将订单资金链路从“模拟支付”升级为真实微信支付与退款闭环。
- 开发范围：
  - 新增支付单、退款单、回调记录和幂等处理事实表。
  - 小程序支付改为由后端创建微信支付单，返回调起支付所需参数；支付成功通过回调或主动查询更新订单支付状态。
  - 管理端退款审批与订单退款状态改为驱动真实退款流程，并处理退款成功、失败、重试和回调。
  - 统一订单状态机与支付状态机在支付成功、退款申请、退款中、退款完成、部分退款下的流转。
  - 保留开发环境 mock fallback，但必须通过环境显式启用，不允许混入正式链路。
- 本 Stage 边界（不做）：
  - 不做完整财务报表。
  - 不扩展多支付渠道。
- 必做测试：
  - `cd sunflower-backend && mvn test`
  - 小程序手工验证：创建订单、调起支付、支付成功回流、退款申请、退款状态变更。
  - 后端集成测试覆盖：重复回调、签名失败、退款失败、回调幂等。
- 完成标准：
  - 订单支付与退款不再依赖模拟接口切状态。
  - 支付/退款具有可追踪的流水号、回调记录和幂等保护。

### S19 生产入口与微信发布阻塞项收口

- 目标：清理正式上线前的环境与发布阻塞项，确保 V1 真正可对外提供服务。
- 开发范围：
  - 小程序 API 地址、管理端 API 地址和支付回调域名全部改为环境化配置，移除公网 IP / `http` 硬编码。
  - 完成 HTTPS 证书、Nginx/ECS 入口、健康检查、CORS/代理和静态资源发布策略确认。
  - 校验并落地微信小程序合法域名、业务域名、支付回调域名、隐私协议/用户协议等发布前配置。
  - 打通 staging / production 的密钥注入、配置回滚、启动烟测、异常告警最小闭环。
  - 更新发布 Runbook、联调清单和故障回退步骤。
- 必做测试：
  - `cd sunflower-admin-web && npm run build`
  - 部署后 smoke test：`/api/health`、管理端登录、小程序登录、小程序下单、支付回调入口可达。
  - 按发布清单完成 1 轮 staging 验收。
- 完成标准：
  - 所有线上入口均使用正式域名与 HTTPS。
  - 微信后台配置、部署配置和应用实际运行配置一致。

### S20 对账、安全收口与 V1 最终验收

- 目标：完成 V1 上线前最后一公里，交付“可运营、可回溯、可验收”的正式版本。
- 开发范围：
  - 补齐支付对账视图、关键运营报表和订单来源/支付来源最小统计口径。
  - 补齐认证与账号安全事件埋点：登录成功/失败、验证码发送、密码重置、支付回调异常、退款异常。
  - 统一小程序、后端、管理端的最终验收清单，覆盖登录、绑手机号、下单、支付、退款、入住、离店、后台登录、密码重置、售后处理。
  - 明确上线准入条件、灰度策略、回滚条件和故障联系人。
- 必做测试：
  - 全量自动化测试通过。
  - 按最终验收清单完成至少 1 轮 staging 和 1 轮 production rehearsal。
- 完成标准：
  - V1 具备正式上线条件，不再存在“认证/支付/生产发布”级别阻塞项。

## 6. 里程碑映射（便于管理）

- M1：S1-S6（后端落库 + 小程序主链路稳定 + 售后补齐）
- M2：S7-S13（后台 API + Web 管理后台 MVP）
- M3：S14-S15（联调收口 + CI + 发布基础 + 订单状态机重构）
- M4：S16-S20（真实认证 + 后台账号体系 + 真实支付/退款 + 生产上线收口）

## 7. 风险前置（执行时持续检查）

1. 微信手机号能力的官方主流程要求小程序主体与认证条件满足微信开放要求，且存在调用成本；若资质未就绪，S16 需明确保留仅开发环境可用的降级方案，但不能把降级方案当作生产标准。
2. 微信支付与退款的真实能力受商户号、证书、回调域名、联调环境影响，S18 必须先完成网关抽象、幂等设计和失败补偿，避免状态机返工。
3. 管理端账号体系涉及密码安全、短信资源、频率限制和审计要求，S17 不能只做“能登录”，必须同时具备最小安全基线。
4. 小程序自动化测试能力弱，必须保留手工验收 checklist，避免“只测后端不测端上”。
5. 每个 Stage 结束必须同步文档，否则计划与代码会再次失真。
